# Kotlin과 Compose

공통 책임 분리 기준을 먼저 적용한다. 아래는 추출 과정에서 보존해야 할 Kotlin/Android의 동작 경계다. 특정 패키지 구조나 MVVM·Clean Architecture 계층 수를 강제하지 않는다.

## Kotlin의 책임과 가시성

- 단일 책임의 타입과 전용 확장 함수·순수 변환은 함께 둘 수 있다. 함수 하나당 파일 하나를 만들지 않는다.
- 파일을 나누려고 `private` 상태를 공개하지 않는다. 파일 간 호출에 필요한 최소 `internal` API만 열고, 상태 변경은 소유자의 연산을 통해 수행한다.
- 거대한 ViewModel의 메서드를 확장 함수로 흩어 놓거나 ViewModel 전체를 새 객체에 넘기는 것은 책임 분리가 아니다.
- 저장소는 저장·조회와 그 불변조건을 맡고, 화면 이동이나 UI 상태를 직접 변경하지 않는다. 작업 결과·오류를 호출자에게 돌려준다. 기존 저장소를 한 번 더 감싸기만 하는 계층은 추가하지 않는다.
- 공통 저장·동기화 작업을 추출할 때 DB 인스턴스의 생성·닫기 시점, 트랜잭션, 파일 정리와 커밋 순서를 유지한다. 실제 재사용이나 독립적인 책임 없이 인터페이스와 구현 클래스를 쌍으로 만들지 않는다.

## Compose의 상태와 생명주기

- 상태마다 소유자를 명확히 하고, 추출한 컴포넌트에서 입력 상태를 별도의 가변 상태로 복제하지 않는다. 기존 소유 위치가 적절하면 유지한다.
- `remember`·`rememberSaveable`의 키, composition 내 호출 위치, 조건부 분기와 저장·복원 범위를 확인한다. 함수 본문을 그대로 옮겼어도 호출 구조가 달라지면 생명주기가 달라질 수 있다.
- `LaunchedEffect`·`DisposableEffect`의 키와 실행·취소·해제 시점을 유지한다. 효과를 여러 하위 컴포넌트에 복제하거나 재구성 때 외부 작업을 직접 시작하지 않는다.
- 화면 진입부는 상태·이벤트 연결을 담당하고, 의미 있는 화면 영역은 필요한 상태와 이벤트를 받도록 나눌 수 있다. 단순 전달용 `Content` 래퍼만 남기는 것은 목표가 아니다.
- 화면 전용 작은 컴포넌트는 가까이 두고, 독립적인 화면·상호작용 책임이나 실제 재사용이 있으면 분리한다. 기존 Material 테마·접근성·테스트 태그를 보존한다.

## 코루틴과 작업 순서

- `viewModelScope` 등 기존 scope와 부모 Job을 보존한다. 파일 분리를 위해 새 독립 scope나 `GlobalScope`를 만들지 않는다. 작업 수명과 정리 책임을 누가 소유하는지 명확히 한다.
- 취소 전파, dispatcher, 오류 처리, 재시도, Flow 수집 횟수를 유지한다. `CancellationException`을 일반 실패로 삼키지 않는다.
- `Mutex`·트랜잭션·세대 번호 등의 동시성 경계를 유지한다. 기존 임계 영역을 임의로 쪼개거나 새 잠금을 추가하지 않고, 잠금의 소유자와 획득 순서를 명시한다.
- 네트워크 작업과 저장 커밋의 기존 순서, 취소 가능 구간 및 `NonCancellable` 범위를 보존한다. 저장소 추출 때문에 네트워크를 잠금 안으로 옮기지 않는다.
- 함께 공개되어야 하는 앨범·시계 같은 상태 사이에 새 suspension 지점을 넣지 않는다. 상태를 분리한 객체마다 중복 보관하지 않는다.

## 적용 예와 검증

- 앨범 목록·상세·재생 설정은 독립적인 화면 책임이면 분리한다. 각 화면의 짧은 전용 레이블·상수까지 별도 파일로 옮기지는 않는다.
- 시계 저장·복구·정리는 저장소 책임으로 추출할 수 있다. ViewModel은 기존 잠금과 상태 반영 순서를 계속 소유할 수 있다.
- 클라우드 처리를 추출하려는데 ViewModel 내부 상태와 콜백을 대량으로 넘겨야 한다면, 먼저 클라우드가 소유할 상태와 호출자에게 돌려줄 결과를 정한다. 파일 이동으로 결합을 숨기지 않는다.
- 검증은 변경 영향에 맞춘다. 기존 테스트로 동작 보존을 확인하고, 필요한 경우 상태 복원·화면 재진입·취소·동시 갱신·저장 실패를 확인한다. 파일 이름이나 줄 수만 검사하는 테스트를 만들지 않는다.
