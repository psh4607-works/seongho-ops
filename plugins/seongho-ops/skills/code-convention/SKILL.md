# Code Convention

사용자의 코드 작성 기준을 프로젝트 맥락에 맞게 적용한다. 기본 응답은 한국어로 한다.

## 적용 범위와 우선순위

- 사용자의 현재 지시와 저장소의 명시적 지침을 우선한다. 충돌하지 않는 영역에 이 스킬의 기본값을 적용한다.
- 먼저 대상 코드, 인접 구현, lint/format 설정, 디자인 시스템과 데이터 페칭 관례를 확인한다. 아래 기본값을 이유로 기존 프로젝트 전체를 일괄 변환하지 않는다.
- 리뷰 요청은 진단으로 수행하고, 작성·수정·리팩토링 요청은 허용된 범위에서 구현한다. 이 스킬 자체는 커밋·푸시·PR 게시·머지를 승인하지 않는다.
- 리팩토링은 동작과 외부 API를 보존한다. 함수 추출이나 파일 분리로 상태 생명주기, 요청 횟수, 오류 전파, 이벤트 실행 순서를 바꾸지 않는다.
- 프레임워크·라이브러리 API는 설치 버전의 문서와 타입으로 확인한다. CSR/정적 배포에 SSR, Server Actions, API 중계 계층을 도입하지 않는다.

## 필요한 상세 기준

- TypeScript 작성, 네이밍·타입·함수·안티패턴 점검: [TypeScript와 선언적 코드](references/typescript.md)를 읽는다.
- React 컴포넌트/Hook 작성·리팩토링, 디자인 시스템·데이터 페칭 점검: [React와 디자인 시스템](references/react.md)을 읽는다. TS/TSX라면 TypeScript 기준도 함께 적용한다.
- 다른 언어에는 아래 공통 원칙만 적용하며 TypeScript의 문법·네이밍을 강요하지 않는다.

## 공통 판단 기준

1. **읽히는 책임 단위**: 함수는 한 가지 역할을 드러내고, 이름은 무엇을 하는지 설명한다. 주 흐름은 early return으로 평탄하게 유지한다.
2. **선언적 데이터 처리**: 변환은 순수함수와 `map`/`filter` 등으로 표현한다. 순차 실행, 조기 종료, 성능상 필요한 반복문은 허용하며 억지로 `reduce`에 구겨 넣지 않는다.
3. **필요한 만큼의 추상화**: 기존 유틸리티를 먼저 재사용한다. 한 번 쓰는 전달용 래퍼, 자명한 한 줄 연산의 헬퍼, 미래 재사용을 가정한 계층을 추가하지 않는다.
4. **가까이 두기**: 전용 헬퍼·fallback·데이터 레이어는 기본적으로 같은 파일에 둔다. 실제 재사용과 독립적 책임이 있을 때 분리한다.
5. **디자인 일관성**: 프로젝트 디자인 시스템을 우선한다. 없으면 shadcn/ui 기반 공통 UI 계층과 토큰을 사용한다. 자세한 선택·확장 기준은 React 참조에 따른다.
6. **경계 유지**: 데이터 접근, UI 상태, 순수 변환, 외부 부작용을 구분한다. 분리 자체가 목적이 되어 흐름을 더 어렵게 만들지 않는다.

## 작업 방식

1. 사용자가 지정한 파일/기능과 작성·리뷰·리팩토링 중 요청 유형을 확인한다. 범위가 없으면 현재 변경 파일을 우선한다.
2. 필요한 참조만 읽고 명시적 규칙 위반, 실제 동작 문제, 선택적 개선을 구분한다.
3. 수정 시 영향을 받는 사용처와 공개 타입을 확인하고 작은 단위로 변경한다. 포매팅은 기존 도구에 맡긴다.
4. 변경 영향에 맞는 lint/typecheck/기존 테스트를 실행한다. 조건 분기, 상태, 비동기 흐름을 바꾸면 관련 회귀 동작을 확인한다. 단순 스타일 변경에 구현을 복제하는 테스트를 추가하지 않는다.
5. 결과에는 핵심 변경 또는 발견 사항, 파일 위치와 근거, 실제 실행한 검증을 짧게 남긴다. 검증하지 못한 부분은 구분한다.

리뷰에서는 근거 있는 문제와 선택적 제안을 분리한다. 임의 점수, 전체 체크리스트 나열, 기존 코드와 무관한 일반론은 생략한다. 코드 컨벤션 점검 결과를 외부 PR 승인으로 표현하지 않는다.
