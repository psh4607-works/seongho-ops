# Code Convention

사용자의 코드 작성 기준을 프로젝트 맥락에 맞게 적용한다. 기본 응답은 한국어로 한다.

## 적용 범위와 우선순위

- 사용자의 현재 지시와 저장소의 명시적 지침을 우선한다. 충돌하지 않는 영역에 이 스킬의 기본값을 적용한다.
- 먼저 대상 코드, 인접 구현, lint/format 설정, 디자인 시스템과 데이터 페칭 관례를 확인한다. 아래 기본값을 이유로 기존 프로젝트 전체를 일괄 변환하지 않는다.
- 리뷰 요청은 진단으로 수행하고, 작성·수정·리팩토링 요청은 허용된 범위에서 구현한다. 이 스킬 자체는 커밋·푸시·PR 게시·머지를 승인하지 않는다.
- 리팩토링은 동작과 외부 API를 보존한다. 함수 추출이나 파일 분리로 상태 생명주기, 요청 횟수, 오류 전파, 이벤트 실행 순서를 바꾸지 않는다.
- 프레임워크·라이브러리 API는 설치 버전의 문서와 타입으로 확인한다. 파일 정리를 이유로 새 아키텍처나 라이브러리를 도입하지 않는다.

## 필요한 상세 기준

- TypeScript 작성, 네이밍·타입·함수·안티패턴 점검: [TypeScript와 선언적 코드](references/typescript.md)를 읽는다.
- React 컴포넌트/Hook 작성·리팩토링, 디자인 시스템·데이터 페칭 점검: [React와 디자인 시스템](references/react.md)을 읽는다. TS/TSX라면 TypeScript 기준도 함께 적용한다.
- Kotlin 코드와 Compose 화면의 상태·코루틴·파일 분리: [Kotlin과 Compose](references/kotlin-compose.md)를 읽는다.
- 그 밖의 언어에는 아래 공통 원칙을 적용하고 해당 언어와 프로젝트 관례를 따른다. 관련 없는 언어별 참조는 읽지 않는다.

## 공통 판단 기준

1. **읽히는 책임 단위**: 함수는 한 가지 역할을 드러내고, 이름은 무엇을 하는지 설명한다. 주 흐름은 early return으로 평탄하게 유지한다.
2. **선언적 데이터 처리**: 변환은 순수함수와 `map`/`filter` 등으로 표현한다. 순차 실행, 조기 종료, 성능상 필요한 반복문은 허용하며 억지로 `reduce`에 구겨 넣지 않는다.
3. **필요한 만큼의 추상화**: 기존 유틸리티를 먼저 재사용한다. 한 번 쓰는 전달용 래퍼, 자명한 한 줄 연산의 헬퍼, 미래 재사용을 가정한 계층을 추가하지 않는다.
4. **응집성**: 같은 이유로 함께 바뀌는 코드를 모은다. 전용 헬퍼는 소유한 책임 가까이에 두되, 독립적인 변경 이유가 있는 책임은 재사용 여부와 무관하게 분리를 검토한다.
5. **디자인 일관성**: 프로젝트와 플랫폼의 컴포넌트·토큰·테마·접근성 관례를 우선한다. 웹 라이브러리 선택은 React 참조에서만 다룬다.
6. **경계 유지**: 데이터 접근, UI 상태, 순수 변환, 외부 부작용을 구분한다. 분리 자체가 목적이 되어 흐름을 더 어렵게 만들지 않는다.

## 파일과 책임의 경계

파일 하나에 함수나 클래스 하나만 두는 규칙은 없다. 같은 기능 이름 아래 있어도 UI, 저장, 동기화의 변경 이유가 다르면 별도 책임일 수 있다. 반대로 화면과 전용 작은 컴포넌트, 저장소와 전용 변환 함수는 같은 책임을 구현할 수 있다.

| 기준 | 분리를 검토할 신호 | 함께 둘 근거 |
| --- | --- | --- |
| 변경 이유 | 서로 다른 요구사항 때문에 독립적으로 변경된다 | 같은 동작을 바꾸면 함께 수정된다 |
| 상태 소유권 | 독립적인 상태와 생명주기를 가진다 | 하나의 상태와 불변조건을 함께 유지한다 |
| 의존성 | UI가 DB·네트워크·파일 처리까지 직접 수행한다 | 전용 구현이 같은 의존성과 책임을 공유한다 |
| 인터페이스 | 작은 입력과 결과로 역할을 설명할 수 있다 | 분리하면 내부 상태·콜백을 대량으로 전달한다 |
| 읽기 비용 | 호출부에서 주 흐름을 이해하기 쉬워진다 | 단순한 흐름도 여러 파일을 왕복해야 한다 |

표는 점수표나 기계적인 판정 조건이 아니다. 실제 사용처·변경 이유·상태 흐름을 근거로 판단한다. 공통 잠금이나 트랜잭션이 있다고 무조건 한 파일에 둘 필요는 없지만, 그 경계의 소유자와 호출 순서는 명확히 유지한다.

- 추출 전에 각 책임이 소유할 상태, 입력·결과, 외부 부작용과 의존 방향을 확인한다. 파일 이동보다 상태 소유권 정리가 먼저 필요한 경우를 구분한다.
- 추출한 단위는 역할을 드러내는 이름과 필요한 최소 인터페이스를 갖는다. 새 공개 API나 공유 가변 상태, 양방향 의존성이 늘어나면 경계를 다시 검토한다.
- 전체 ViewModel·서비스 객체를 전달하거나 내부 상태를 공개해서 분리를 성립시키지 않는다. 인자를 임의의 Context/Manager 객체에 묶어 결합을 숨기지도 않는다.
- 독립적인 책임은 사용처가 하나여도 분리할 수 있다. 반대로 미래의 재사용 가능성, 줄 수, 함수 개수만으로 파일을 나누거나 공통 계층을 만들지 않는다.
- `Utils`, `Helpers`, `Common`에 서로 무관한 기능을 모으지 않는다. 이름을 바꾸는 것만으로 관심사가 분리되었다고 보지 않는다.
- 전용 순수함수·상수·작은 하위 컴포넌트는 해당 책임 가까이에 둔다. 전달만 하는 래퍼와 자명한 한 줄 헬퍼로 흐름을 잘게 쪼개지 않는다.
- 역할과 의존성이 명확하고 변경 흐름을 따라가기 쉬워졌다면 멈춘다. 요청 범위 밖의 거대 파일이나 프로젝트 전체를 자동으로 재구성하지 않는다.

## 작업 방식

1. 사용자가 지정한 파일/기능과 작성·리뷰·리팩토링 중 요청 유형을 확인한다. 범위가 없으면 현재 변경 파일을 우선한다.
2. 필요한 참조만 읽고 명시적 규칙 위반, 실제 동작 문제, 선택적 개선을 구분한다.
3. 수정 시 영향을 받는 사용처와 공개 타입을 확인한다. 분리 후보는 위 기준으로 판단하고, 상태 소유권과 동작을 보존하며 작은 단위로 변경한다. 포매팅은 기존 도구에 맡긴다.
4. 변경 영향에 맞는 lint/typecheck/기존 테스트를 실행한다. 조건 분기, 상태, 비동기 흐름을 바꾸면 관련 회귀 동작을 확인한다. 단순 스타일 변경에 구현을 복제하는 테스트를 추가하지 않는다.
5. 결과에는 핵심 변경 또는 발견 사항, 파일 위치와 근거, 실제 실행한 검증을 짧게 남긴다. 검증하지 못한 부분은 구분한다.

리뷰에서는 근거 있는 문제와 선택적 제안을 분리한다. 임의 점수, 전체 체크리스트 나열, 기존 코드와 무관한 일반론은 생략한다. 코드 컨벤션 점검 결과를 외부 PR 승인으로 표현하지 않는다.
